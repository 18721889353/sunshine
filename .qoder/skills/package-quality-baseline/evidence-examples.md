# 实测证据：合格样例与反例

全部条目来自 `pkg/nacoscli` 真实排障过程，不是构造的示例。用途：写注释/README/CHANGELOG 时对照自查。

## 一、合格：结论 + 读数 + 环境 + 轮数

> **已在真实 Nacos 环境验证**（公网实例，2 轮全绿）：预热 3s 后发生的变更均被收到，
> 外部 Open API 变更首次送达 2.27s / 2.267s，后续送达 233ms / 210ms，未出现丢事件。

合格的四个要素齐了：**环境**（公网 Nacos 实例）、**轮数**（2 轮）、**读数**（逐轮列出而非取平均）、**结论**（不丢事件）。

延迟表更完整的形态（README 用）：

| 场景 | 送达延迟 |
|------|----------|
| 建立监听后的**第一次**变更 | 2.264s / 2.267s / 2.27s / 2.283s（4 轮） |
| 随后的变更 | 210ms / 233ms / 269ms / 275ms |
| **空闲 15s 后**的变更 | 220ms / 221ms（证明长连接不会因空闲失效，监听也不是一次性消耗） |

多轮读数用「逐个列出」而不是「平均 1.2s」——平均值会掩盖首次延迟比后续高一个数量级这一事实，
而那个差异本身就是有用的信息（首次要走注册生效 + 服务端推送建立）。

## 二、合格：把故障特征原文写进注释

> 实测证据是 SDK 日志（`os.TempDir()/nacos/log/nacos-sdk.log`）中的
> `Send request fail, request=ConfigQueryRequest ... error=client not connected, current status:STARTING`。

**原始 error 文本 + 去哪里看**，比「连接没建立」有用得多：下次同样报错能直接 grep 定位。

同类：

> 实测 HTTP 32564 / gRPC 32566，推导值 33564 不存在 ⇒ 必须 `WithServerConfigs` 显式指定 `GrpcPort`。

## 三、合格：假设被推翻 → 记下误判过程

> 本轮曾误判为「缓存异步填充延迟」并加了轮询，读数不变才暴露出真正原因是过滤语义。

真因定位到源码条件（这才叫取证）：

```
naming_client.go 的 selectInstances：
    if host.Healthy == healthy && host.Enable && host.Weight > 0
⇒ HealthyOnly 缺省（false）时**只返回不健康实例**，与 HTTP API 的 healthyOnly=false（返回全部）相反
```

附带做的影响面核对（区分「测试写错」与「线上有 bug」）：

> 生产侧无此问题：`pkg/servicerd/registry/nacos/registry.go` 三处调用均显式传了 `HealthyOnly: true`。

**要点**：误判不删掉、写成「曾判为 X，证伪证据是 Y」。删掉等于把最贵的一课扔掉。

## 四、合格：只写现象，不写未取证的原因

现场：连续注册 3 个临时实例后只发现 1 个。

**没取证前**不能写「集群同步延迟」。做法是补两份视图：

```
注册第 1 个实例后服务端快照: [10.0.0.10:8080(healthy=true)]
注册第 2 个实例后服务端快照: [10.0.0.10:8080(healthy=true)]
注册第 3 个实例后服务端快照: [10.0.0.10:8080(healthy=true)]
未达预期 -> SDK 健康实例=1(轮询20次), SDK 缓存实例=1
服务端快照第 1 次: [10.0.0.12:8082(healthy=true)]
服务端快照第 2 次: [10.0.0.12:8082(healthy=true)]
```

读数支持的结论只到这里：

> SDK 侧与服务端 Open API 侧**都只看到 1 个**，且不同时刻看到的那 1 个还会变
> ⇒ 多个临时实例并未在该服务端节点上聚合，属 Nacos 部署层面现象，**不是本包代码缺陷**。

「不同时刻那 1 个会变」是关键一条：它排除了「服务端确实只有 1 个」，指向读取路径落在不同节点。
但仍**没有**断言是 Distro 同步失效——那一层需要服务端日志才能取证，不在本包职责内。

## 五、合格：断言降级必须同批附证据

> 因此断言只覆盖「已注册实例能被列举到（≥1）」这一可稳定复现的事实，
> 把「看到几个」降级为记录，避免用一条永不满足的断言掩盖真实原因。

降级的三个条件齐了才算合格：① 有实测读数；② 说清归属（环境层面）；③ 保留诊断输出，下次能复现判断。

## 六、反例：过期的「未验证声明」没删

曾经写在注释里的句子：

> **取值是经验余量而非实测**（且本轮未在有真实 Nacos 的环境下跑过，仅 `-tags=integration` 编译验证）

后来真的跑通了集成测试，这句话**没同步删**，于是 README/注释里出现「自称没验证过的已验证结论」。
这就是最典型的假信息生成方式——不是编造，而是**事实变了却没回头改旧陈述**。

自查命令（找出还在自称未验证的地方）：

```bash
grep -rn "本轮未\|未跑过\|未验证\|经验余量而非实测" pkg/*/
```

## 七、反例：把「收到任意一次回调」当通过

`ListenConfig` 是非阻塞注册，注册动作之前发生的变更可能被补推一次。
若断言写成「收到过回调」，则会用一次与本次修改无关的回调通过测试。

正确做法：**按内容匹配**等待，并把「此前收到其它回调 N 次」记进日志。

## 八、反例：关键词归类把故障说成预期

把 `config encrypted data key` 加进「预期失败」关键词后：

```
read config from both server and cache fail, err=read cache file Config Encrypted Data Key failed.
cause file doesn't exist, file path: .../fuliApiGo@@local@@.: file not exist
```

这段文本表达的是**缓存文件不存在**（gRPC 不可达的后果），却被当成「配置已加密，无密钥」放过，
4 个用例静默变绿。**任何按字符串归类错误的判定表，都要写清「为何某个词不能加进来」。**

## 九、反例：本机跑不通却写成已验证

`-race` 在 Windows/MinGW 报 `exit status 0xc0000139`（gcc 运行时问题，与包代码无关）。

合格写法：

> 诚实声明：当前开发机执行 `-race` 会报 `exit status 0xc0000139`，因此本 README **不声称已经跑过 `-race`**，
> 只给出已验证过的命令形式；真实证据需在 Linux/CI 上采集。

## 十、基准读数的口径也要当证据写

> `ClientGetConfig` 基于包内 `mockConfigClient`，**不含任何网络 RTT**，它量的是「本包自己的开销」

以及稳定性口径：

> 同一命令四次重测得到 312/418/486/488ns（±40%），而分配恒为 3 次
> ⇒ 需要区分优劣时看 `allocs/op`（稳定）而不是 `ns/op`（本机波动大）

**读数不可信时，可信指标 + 波动指标要分开说**，否则一张表里的数字会被当成精确结论。
