## 二、「前提条件」小节模板（监听/异步/长连接类能力必写）

这类能力最容易「代码没错但不生效」，必须把生效前提与实测延迟写在一起：

```markdown
**<能力> 生效的 N 个前提**（均在 <环境> 实测过，任一条不满足则 <典型故障现象>）：

1. **<前提一>**。实测 <读数和错误特征>，不满足时报 `<原始 error 文本>`。
2. **<前提二>**。实测 `<HTTP 状态/Code/Message>`。
3. **<前提三>**：外部库未暴露「已生效」信号，需预热窗口。实测延迟如下：

   | 场景 | 送达延迟 |
   |------|----------|
   | <首次> | <多轮读数> |
   | <后续> | <多轮读数> |
   | **空闲 <N>s 后** | <读数>（证明<不是一次性消耗/连接不因空闲失效>） |

   验证入口：`TestIntegration_<Name>`——它的<触发方>走 <外部真实入口>，
   被测方全程<只读/只监听>，因此它证明的是真实运维场景：<一句话结论>。
```

## 三、README「集成测试」章节模板

````markdown
## 集成测试

集成测试带 `//go:build integration` 构建标签，依赖真实 <服务> 服务，通过环境变量配置。

**环境变量一览**（与 `integration_test.go` 实际读取的变量一一对应）：

| 变量 | 必填 | 用途 | 默认值 |
|------|------|------|--------|
| `<SVC>_IP_ADDR` | 是* | <用途>，未设置时全部集成测试自动 Skip | 无 |
| `<SVC>_TEST_TIMEOUT` | 否 | `TestMain` 总时长上限（Go duration） | `120s` |

\* <组合必填条件说明>

**运行方式**：

```bash
cd pkg/<name>

# 方式一：显式传环境变量（CI 用法，优先级高于 .env）
<SVC>_IP_ADDR=... go test -tags=integration -v -count=1

# 方式二：包内 .env（推荐本地，无需任何插件）
# `TestMain` 里的 `loadDotEnv` 会自动读取包内 .env 并补齐环境变量，
# 语义是「只补缺、不覆盖已设置的变量」；根 .gitignore 的 `*.env` 已覆盖该文件，不会入库。
go test -tags=integration -v -count=1

# 只跑某一组（注意：多个用例名之间不要直接用 `|`，Git Bash 会把 `|` 当管道）
go test -tags=integration -count=1 -v -run '<无竖线的正则>'

# 仅单元测试（无需任何环境变量，日常使用）
go test ./pkg/<name>/ -v
```

**行为说明**：
- 未设置必需变量时依赖服务的测试自动 Skip，单元测试不受影响
- 等待时长已抽为命名常量（<列出>）而非散落的 `time.Sleep`；出现 flaky 时**优先调这些常量，不要改断言**
- `TestMain` 限制总时长，防止外部 SDK goroutine 泄漏导致 `go test` 永远挂起

**实测结果汇总**（<环境>，`go test -tags=integration -count=1`，总耗时 ~<N>s）：

| 分组 | 结果 | 关键读数 |
|------|------|----------|
| <组> | PASS / SKIP（原因） | <读数> |

**环境限制记录**（属部署层面，不是本包缺陷）：
1. **<外部库语义陷阱>**：<条件> 时 <反直觉行为>，与 <对照接口> 含义相反。
   生产侧不受影响：<已核对的调用点与传参>。
````

## 五、CHANGELOG 模板

```markdown
# Changelog

本文件记录 `<pkg/name>` 的显著变更。

## Unreleased

### 新增
- **<一句话结论作为加粗标题>**：<做了什么 + 为什么 + 关键实现点>
- **文档/测试类变更同样登记**，不要只登代码变更

### 变更
- <行为/签名/默认值变化；破坏性变更必须写清影响面与迁移方式>

### 修复
- **<问题标题>（<风险类别，评审编号>）**：<根因> → <修复方式>；
  若曾误判，写「先判为 X，<证伪证据> 才暴露真因是 Y」
  - 影响面：<哪些输入/路径受影响，哪些不受影响>
  - 守护：<新增/更新了哪个测试来防回归>

### 兼容性说明
- <与相邻包的方案对齐关系；跨包规范的统一边界指向哪个文件>
```

**写作要求**：

1. 每条以**加粗结论**开头，冒号后接证据/原因，让人扫标题就能读懂
2. **修复类条目三要素**（参考 `pkg/logger/CHANGELOG.md` Round 5）：
   - 标题里放**风险类别**——让 grep 能按「生产日志量暴涨」「数据损坏」「阻断级」等词定位
   - 括号里放**评审编号**，统一 `R<轮次>-<原编号>` 格式（如 `R5-P0-1`、`R6-§四-1`）——
     轮次与严重级别一眼可溯，「哪次评审提出的」可 1 秒追溯；禁止裸 `P0-1`（丢失轮次信息）
   - **影响面独立成行**——不读 diff 就能判断「这次改动影响谁」
3. **每轮评审收口独立小节**：`### 第 N 版评审收口（Round N）`，不把两轮混在同一节
   （反面例：Round 5 节内引用「第六轮评审」会让读者困惑归属，已拆节修正）
4. 实测过的写读数；未实测的写「本轮未在 <环境> 验证，仅 <编译/静态检查> 通过」
5. **过期声明必须删掉**，不要保留「历史上以为没跑过」的旧句子——它是假信息的主要来源
6. 不写 commit hash、不写日期（版本发布时再补），避免与 git log 重复
